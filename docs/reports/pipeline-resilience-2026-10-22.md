# 갱신·검증·배포 구조 안정화

기존 수집기와 연결 기준을 유지하면서 정상 개선, 검토 대기, 일시적 가용성 문제, 공통 검증 오류를 서로 다른 경로로 처리한다. 외부 서비스 장애나 모든 새로운 게임 구조의 오류가 사라진다고 보장하지 않는다. 불확실한 연결을 확정하거나 검증 기준을 낮추지 않았다.

## 처리 경계

| 상황 | 처리 |
| --- | --- |
| 검증한 정상 개선 | 원래 보존·원문·검색·언어·빌드 계약을 통과한 동일 산출물만 게시 |
| 특정 장의 BWIKI 후보 충돌 | 해당 장의 본문과 근거를 마지막 정상 상태로 유지하고 후보를 격리 |
| 충돌 장의 신규 공식 원문 후보 | 등록된 수록 후보라면 행·검색·개수·목차·근거를 함께 보류; 다른 장의 수록은 유지 |
| 공개 배포 기준본의 일시적 조회 실패 | `deferred`; 수집·빌드·배포·완료 승인을 생략하고 정기 재시도 |
| 원문·공식 실행 손상, 체크섬 오류, 공통 코드 오류 | 자동 반영 중단; 정상 배포와 조사 기록 보존 |

## 구조 변경

- `verification-state.mjs`의 공통 쓰기 트랜잭션을 스냅샷 복원, 파생 데이터 게시, 장별 격리 복원에서 사용한다. 전체 대상 사전 검사 후 쓰며 뒤쪽 파일의 쓰기 오류 시 이전 바이트와 새 파일의 부재를 복구한다. 복구 실패도 예외로 보고한다. 프로세스 강제 종료나 디스크 자체 장애까지 원자적으로 처리한다고 주장하지 않는다.
- `prepare-verification.mjs`는 원격 스냅샷을 별도 폴더에서 비교하고 선택을 끝낸 뒤 본문을 변경한다. 비교 충돌이 있어도 저장소 고유 근거를 먼저 덮어쓰지 않는다. 비교 보고서는 Actions 증거에 남긴다.
- `content-watch.json`과 `official-videos.json`을 복구 스냅샷과 최종 빌드 봉인에 포함했다. 처리 수정본 기록을 봉인 앞으로 옮겨 테스트 후 입력이 바뀌지 않게 한다. 코드 전용 배포가 변경 감지 기준을 잃어 불필요한 전체 갱신을 반복하지 않게 한다.
- 장별 격리는 기존 원문 ID 집합이 같은 경우뿐 아니라 등록된 원문 우선 수록 후보가 있는 경우도 처리한다. 보류 장의 추가 행을 검색·목차·개수에서 함께 빼고 수록 근거를 이전 상태로 맞춘다. 후보는 삭제하지 않고 격리 증거로 남긴다. 격리 전 비교와 게시 직전 비교를 별도 필드로 기록한다.
- 공개 기준본의 일시적 전송 실패만 명시적인 가용성 예외로 분류한다. `ready=false`인 실행은 워크플로의 후속 갱신을 실행하지 않으며, 기존 pending digest를 승인하거나 실패를 변경 없음으로 기록하지 않는다. JSON/체크섬 오류는 이 경로에 포함하지 않는다.
- 공통 상태·게시 모듈 변경도 재검증 코드 해시에 포함한다. 검증 코드/정책/입력의 재사용 계약은 유지한다.

## 격리 및 회귀 검사

실제 저장 자료의 원문 163행 추가 전 기준본과 현재 후보를 이용해, 신규 원문 16행이 있는 장의 기존 선택지 간선을 고의로 손상시켰다. 새 처리 경로는 해당 장과 16행을 함께 보류하고 다른 장의 147행 수록 후보를 유지했다. 최종 2,840개 본문·67,635행의 검색·원문·3개 비교 언어 계약과 기존 검증/분기/출현/ID 보존 검사를 통과했다. 이는 운영 신규 수록 실적이 아닌 실패 주입 실험이며 운영 데이터는 이 후보로 변경하지 않았다.

별도 실패 주입은 서로 다른 고유 검증을 가진 배포본, 스냅샷 복원 중 뒤쪽 쓰기 실패, 새 파일 롤백, 롤백 자체 실패, 잘못된 경로, 임시 429/503/네트워크 오류, 손상 체크섬, 봉인 후 메타데이터 변경을 다룬다. 64비트 해시 바이트와 기존 JSON 끝 공백에 대한 게시 호환성도 유지했다.

테스트 129개가 통과했다. 실험 증거는 `.cache/pipeline-resilience`에 저장했다. 자동 재검증 및 실제 배포 결과는 완료 후 추가한다.
